# Settings Page Implementation Plan

## Overview

Build a standalone Settings page accessible via `/settings` route (with optional `?project_id=` query param). Clicking the Settings button in Navigation navigates to this page. The page fetches settings from the backend, displays them in two side-by-side columns (Application vs. Project scoped), and allows editing with per-input reset buttons.

---

## Backend Changes

### 1. Update `list_settings` endpoint

**File:** `patchsorter/api/v1/settings/routes.py`

**Change route:** `/projects/{project_id}/settings/` → `/settings/`

**Make `project_id` optional:**

```python
@router.get("/settings/", response_model=List[ResolvedSetting])
def list_settings(project_id: Optional[int] = None) -> List[ResolvedSetting]:
    client = get_head_client()
    with client.get_session() as session:
        store = SettingsStore(session)
        rows = store.get_all_raw(project_id=project_id)
    return list(rows.values())
```

- When `project_id` is `None`: returns only application-scoped settings
- When `project_id` is provided: returns both application and project-scoped settings

### 2. Add `update_setting` endpoint

**File:** `patchsorter/api/v1/settings/routes.py`

```python
from pydantic import BaseModel


class UpdateSettingRequest(BaseModel):
    value: str


@router.patch("/settings/{setting_key}", response_model=ResolvedSetting)
def update_setting(
    setting_key: str,
    body: UpdateSettingRequest,
    project_id: Optional[int] = None,
    session: Session = Depends(get_head_session),
) -> ResolvedSetting:
    store = SettingsStore(session)
    try:
        store.update(setting_key, body.value, project_id)
    except SettingDisabledError:
        raise HTTPException(status_code=403, detail=f"Setting '{setting_key}' is read-only")
    except ValueError as e:
        raise HTTPException(status_code=422, detail=str(e))
    session.commit()
    resolved = store.get_raw(setting_key, project_id)
    return resolved
```

- `PATCH /settings/{setting_key}?project_id=...`
- Validates disabled settings → 403
- Validates type/enum constraints → 422
- Returns updated `ResolvedSetting`

## Frontend Changes

### 3. New file: `patchsorter/client/src/pages/SettingsPage.tsx`

**Route:** `/settings` with optional `?project_id=` query param

**Structure:**

```
SettingsPage
├── Application Settings (always shown)
│   └── SettingInput for each application-scoped setting
└── Project Settings (only if project_id present)
    └── SettingInput for each project-scoped setting
```

**SettingInput component (per-setting):**

| `type` | Input component | Notes |
|--------|----------------|-------|
| `enum` | `<FormSelect>` dropdown | Options from `allowed_values` |
| `boolean` | `<FormCheck>` checkbox | Internally stores `"true"`/`"false"` strings |
| `integer` | `<FormControl type="number">` | Numeric input |
| `string` | `<FormControl type="text">` | Free text |

**Per-input features:**
- `disabled` prop on the input when `ResolvedSetting.disabled === true`
- **Reset** button next to each input → calls `PATCH /settings/{key}?project_id=...` with the `default` value
- **Save** button at the bottom of each column section → batches all changed inputs

**State management:**
- `useQuery` to fetch settings list
- `useMutation` for update calls
- `useQueryClient` to invalidate/refetch after updates
- Local state tracks `dirty` inputs per column to know what has changed

### 4. Update `patchsorter/client/src/main.tsx`

Add `/settings` route as a child of Root so Navigation is visible:

```typescript
{ path: '/settings', element: <SettingsPage /> },
```

Import and register the new SettingsPage component.

### 5. Update `patchsorter/client/src/components/Navigation.tsx`

Change the Settings link from a plain `Nav.Link` to a proper `<Link>`:

```tsx
<Nav.Link as={Link} to="/settings" className="text-white">
    Settings
</Nav.Link>
```

### 6. Regenerate client SDK

After adding the update endpoint, regenerate the TypeScript client:

```bash
cd patchsorter/client && npm run generate
```

This updates `src/api_client/` with the new `updateSetting` function and types.

## Key Design Decisions

- **Standalone page, not modal**: Consistent with the user's request for a dedicated page
- **Optional project_id**: Settings page works without a project (shows only application settings); with project_id, shows both columns side-by-side
- **Per-input reset**: Each setting has its own reset button to revert to the schema default
- **React Query**: Uses `useMutation` + `useQueryClient` for updates with automatic cache invalidation
- **react-bootstrap**: Uses existing Bootstrap components (FormSelect, FormCheck, FormControl, Button) to match the app's styling
