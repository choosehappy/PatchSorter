## Summary

The codebase shows a research-focused implementation for an active learning embedding system targeting ≥1B objects with progressive rendering capabilities. Overall, the project structure is reasonable and follows domain-specific guidelines around incremental inference and loss function modularity. However, there are several critical issues that need addressing before this can be considered merge-ready:

1. **Critical Issues**: 
   - Missing `from __future__ import annotations` in multiple files
   - No type hints on public functions (except one file)
   - Lack of proper logging throughout the codebase
   - Inconsistent use of random seeds for reproducibility

2. **High Severity**:
   - The main pipeline (`start_v1.py`) has no clear separation between embedding and 2D layout stages, which violates the progressive rendering requirement.
   - Several loss components are not independently testable due to tight coupling.

3. **Merge Readiness**: 
   This codebase is not ready for merging in its current state. Critical issues around type safety, logging, and reproducibility must be addressed first. The pipeline structure also needs refactoring to support online/incremental inference as required by the project goals.

## Scalability & Efficiency Highlights

### [CRITICAL] Exact kNN over full dataset
**File:** `./start_v1.py` **Line:** 20
**Category:** Scalability
**Detail:** The code uses exact kNN computation over the entire dataset which is infeasible at ≥1B scale.
**Suggestion:** Replace with approximate nearest neighbor search (e.g., FAISS, HNSW) for large-scale scenarios.

### [CRITICAL] Collecting all embeddings into a single in-memory tensor
**File:** `./start_v1.py` **Line:** 20
**Category:** Scalability
**Detail:** The code collects all embeddings into memory which will cause out-of-memory errors at ≥1B scale.
**Suggestion:** Stream or shard embeddings; use memory-mapped arrays for large datasets.

### [HIGH] Missing `torch.no_grad()` during inference
**File:** `./start_v1.py` **Line:** 20
**Category:** Scalability
**Detail:** The code does not wrap inference calls in `with torch.no_grad():`, which unnecessarily builds autograd graphs.
**Suggestion:** Wrap all inference operations with `with torch.no_grad():` to reduce memory usage.

### [HIGH] DataLoader missing `num_workers` > 0
**File:** `./utils.py` **Line:** 15
**Category:** Scalability
**Detail:** The DataLoader does not use multiple workers, which creates a CPU bottleneck at high throughput.
**Suggestion:** Set `num_workers` to the number of CPU cores (typically 4–8) for better performance.

### [HIGH] DataLoader missing `pin_memory=True`
**File:** `./utils.py` **Line:** 15
**Category:** Scalability
**Detail:** The DataLoader does not use pinned memory, which slows down host→GPU transfers.
**Suggestion:** Enable `pin_memory=True` when using CUDA for faster data transfer.

## AGENTS.md Compliance Checklist

### Code Style
- [ ] `from __future__ import annotations` present in every module
- [ ] Import order: stdlib → third-party → local (blank line between each group)
- [ ] No wildcard imports (`import *`)
- [ ] Type hints on all public function signatures (parameters + return value)
- [ ] Built-in generics used for 3.8 compat (`list[x]` → `List[x]` from `typing`)
- [ ] No bare `print` statements — `logging` used throughout
- [ ] Naming: `snake_case` functions/variables, `PascalCase` classes, `UPPER_CASE` constants, `_single_underscore` private

### Documentation
- [ ] NumPy-style docstrings on all public functions, classes, and modules
- [ ] Docstrings cover: Parameters, Returns, Raises, and algorithmic notes where relevant
- [ ] Loss weight defaults are justified in docstrings or inline comments
- [ ] Comments explain *why*, not *what*

### Reproducibility
- [ ] `torch.manual_seed` and `numpy.random.seed` set and documented in configs
- [ ] Model checkpoints stored co-located with their config files

### Pipeline
- [ ] Online/incremental inference supported — 2D coords emitted per batch, no full-epoch wait
- [ ] No training loop that blocks output until epoch completion
- [ ] Each pipeline stage is independently benchmarkable

### Loss Functions
- [ ] Each loss component is an independent, importable module
- [ ] Every loss module exposes a `weight` parameter with a documented default
- [ ] All loss components are logged individually per step (not just the combined total)

### Scale
- [ ] No unbounded state accumulation over batches
- [ ] No O(n²) operations over the full dataset
